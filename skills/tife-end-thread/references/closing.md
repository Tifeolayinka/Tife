# Closing a thread

An explicit request to finish, close, cancel, or supersede the work can close its record. A user
leaving for the day or clearing context usually needs session preparation, not closure. Resolve
unclear intent before archiving. Do not require another confirmation for an unambiguous authorized
closure; surface incomplete work and record its disposition.

1. Identify the thread and read its latest contents and relevant documents.
2. Reconcile the final state from evidence. Record outcome as completed, cancelled, or superseded,
   and preserve actual test status, limitations, and any uncertainty.
3. Promote durable requirements, decisions, lessons, and corrections into the appropriate context.
   Create missing context where the work established useful knowledge. Reconcile tests as needed.
4. Route every unfinished item to an existing tracker or another active thread. If no tracker
   exists, create the local open-issues file. Do not silently drop items or assign people. A user
   may explicitly cancel an item; record that decision and reason when supplied.
5. Verify destination files and links before archiving. If saving durable context or routing an
   item failed, leave the thread active and report the concrete failure.
6. Set status closed, outcome, and closed timestamp. Move to the archive without deleting it.
   Rebase relative links inside the moved document and update inbound references and indexes.
   If the archive destination already exists, stop and resolve the conflict; never overwrite it.
7. Summarize the outcome, verification, archive location, and destinations of remaining work.

Keep unrelated threads unchanged. Closure does not automatically commit, push, merge, deploy,
send a teammate message, or clean other project files. If Git operations are independently
authorized, include only the intended changes and report their actual results.
